## Текущее состояние

В данный момент написан парсер документа. Преобразования отсутствуют (вместо них пока заглушка), и нужно понять, не теряем ли мы информацию, перегоняя документ в распарсенное состояние и обратно.

Пока работаем только с DOCX. Задача тестирования: убедиться, что при **пустом** преобразовании результат совпадает с оригиналом. При пустом преобразовании эталон известен заранее, поэтому любое отличие результата от оригинала является дефектом.

### Структура модуля

```
parser/
├── __init__.py    # публичный интерфейс
├── converter.py   # parse: файл -> DoclingDocument (Docling)
├── storage.py     # save / load: DoclingDocument <-> document_<timestamp>.json + папка assets
├── editor.py      # extract / apply_edits: правка текста в самом DOCX
└── verify.py      # check_assets: проверка, что вложения и связи не потерялись
```

### Как устроен пайплайн

`DoclingDocument` не хранит стиль: шрифты, поля, колонтитулы, разделы и нумерация в нём не сохраняются. Поэтому документ для пользователя собирается не из разметки Docling, а правкой копии оригинала:

```
original.docx ──► extract: {id: текст} ──► преобразование (ИИ) ──► {id: новый текст}
      │                                                                  │
      └────────────── apply_edits: правки в копии оригинала ◄────────────┘
                                   │
                              edited.docx
```

- `extract` обходит абзацы тела, таблиц (включая вложенные) и колонтитулов и даёт каждому устойчивый ID вида `body/t0/r1/c2/p0`.
- `apply_edits` копирует документ и меняет текст только в абзацах, указанных в `edits`. Оформление абзацев, таблицы, поля страниц, картинки и вложения остаются в XML оригинала.
- Docling (`parse`, `save`, `load`) нужен для разметки под RAG и анализ. Результат сохраняется как `document_<timestamp>.json`, рядом лежит папка `document_<timestamp>_assets/` с картинками и копией исходного файла. В возврате документа он не участвует.

### Флаг `force`

`force` это параметр `apply_edits`: он заставляет переписать **каждый** абзац из `edits`, даже если новый текст совпадает со старым.

Без `force` абзацы с неизменённым текстом пропускаются. Поэтому при пустом преобразовании (`edits` равен результату `extract`) код замены текста вообще не вызывается, и тест проверяет только то, что `python-docx` открыл и пересохранил файл. С `force=True` каждый абзац переписывается тем же самым текстом, и любое отличие от оригинала означает, что сам механизм замены портит документ.

Поэтому каждый случай ниже прогоняется дважды:

| Прогон | Вызов | Что проверяет |
|---|---|---|
| Без `force` | `apply_edits(src, dst, texts)` | Пересохранение файла через `python-docx` |
| С `force` | `apply_edits(src, dst, texts, force=True)` | Механизм замены текста (`_set_text`) |

В обычной работе `force` не нужен, по умолчанию он выключен.

### Известные ограничения

- Не извлекаются и не меняются (но и не должны портиться): текстовые блоки и фигуры с текстом, сноски, комментарии, содержимое полей (например, оглавление), текст внутри графиков и встроенных объектов.
- Колонтитулы первой страницы и чётных страниц `extract` не обходит.
- Абзацы внутри элементов управления содержимым (content controls), вероятно, не видны.
- `\t` и `\n` в тексте правок записываются буквально, а не как табуляция и разрыв строки.
- ID абзацев привязаны к порядку обхода, поэтому `extract` и `apply_edits` должны работать с одним и тем же файлом.
- PDF в этой схеме не поддерживается: PDF не хранит абзацы, поэтому возврат документа с сохранением вёрстки для него отдельная задача.
